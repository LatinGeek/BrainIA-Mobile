## 1. What changed

### 1.1 v2 bearer credential lifecycle (G-V2-AUTH)

`lib/storage.ts` now owns the lifecycle of the token consumed by `lib/api.ts`:

| Operation | Function | Behavior |
| --- | --- | --- |
| Read | `readV2AccessToken()` | Per-request read from Keystore-backed SecureStore; returns `null` when missing, revoked, expired, unreadable, or absent. |
| Status | `readV2Credential()` | Non-secret snapshot (`unconfigured`, `active`, `expired`, `revoked`, `recovery_required`) for UI. |
| Enrollment | `enrollV2AccessToken({ token, expiresAt? })` | The only provisioning path; validates shape, rejects already-expired input, writes token then metadata. |
| Rotation | `rotateV2AccessToken(...)` | Replaces the token in place, increments a monotonic generation, records `rotatedAt`. |
| Revocation | `revokeV2AccessToken()` | Writes the revocation marker first, then deletes the token, so a crash cannot resurrect it. |
| Logout | `logoutV2Session()` | Revokes and deletes the token; leaves an explicit `revoked` record instead of silently returning to `unconfigured`. |

Storage rules:

- Storage key `brainia_mobile.v2AccessToken` (exported as `V2_ACCESS_TOKEN_KEY` from `lib/storage.ts` and re-exported by `lib/api.ts`, so the M01 reader key is unchanged).
- Metadata lives beside it in SecureStore (`brainia_mobile.v2AccessTokenMeta`) as a versioned record (`version: 2`, `generation`, `issuedAt`, `expiresAt`, `rotatedAt`, `revokedAt`).
- No plaintext preference copy exists. Native code has no v2 token writer or reader; the token never enters `SharedPreferences`, `AsyncStorage`, diagnostics, or the JS bundle.
- Writes are serialized per key through the existing write queue (generalized from `credentialWrites` to `serializedWrites`).
- On web, where there is no Keystore and `localStorage` is plaintext, the v2 credential is **memory-only**: a reload requires re-authentication rather than persisting a bearer secret in browser storage.
- On iOS the token/meta are written with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` so Keychain sync/restore cannot move the bearer credential to another device.
- Token validation accepts 16–4096 printable ASCII characters with no whitespace; the value is never logged, echoed, or included in an error message.

Enrollment is an explicit user action in `app/settings.tsx` → *Avanzado* → *Sesión de datos v2*: open sheet, paste credential, optional expiry (ISO-8601 or epoch ms), save. The UI offers rotate, revoke (destructive confirmation), and logout (destructive confirmation), shows generation/expiry, and never renders the stored value again. `allowCredentialRecovery('v2AccessToken')` is required before replacing a credential that previously failed to read; explicit enrollment clears that recovery latch.

`lib/api.ts` now resolves `config.accessToken` when supplied, otherwise `readV2AccessToken()` per request. `lib/app-state.tsx` was **not** modified (outside the write reservation); no app-state wiring is needed because the transport resolves storage at call time.

### 1.2 Explicit empty selection vs unconfigured (versioned consent)

Native consent is now a versioned record:

- `captureConsentState = "configured"` and `captureConsentVersion = 2` are written atomically with `captureAppPackages` by `NotificationBridgeConfig.writeCaptureConsent`.
- Presence of either the v2 state key or the legacy selection key means configured. No key at all means `unconfigured`.
- Configured + empty set means `empty` (an explicit pause) and is reported distinctly from `unconfigured`; both capture zero notifications.
- Upgrade migration: a legacy `captureAppPackages` key is read once, normalized (trimmed, blanks dropped), and rewritten with the version marker by `readCaptureConsent` before the status is returned. A legacy **empty** set migrates as `empty`, not as `unconfigured`, so an intentional pause is preserved.
- `NotificationBridgeService.shouldCapture` and `NotificationBridgeModule.getInstalledCaptureApps` both use the same resolver, so posted, reconciled, and forwarding paths agree with the status API.
- `NotificationBridgeStatus.captureConsentVersion` is surfaced to JS (`lib/notification-bridge.ts`).

### 1.3 Backup and diagnostics

- `AndroidManifest.xml` already sets `android:allowBackup="false"` plus both custom rule references; both XML rule sets exclude `sharedpref`, `device_sharedpref`, `file`, `database`, `root`, `external`, and device-protected variants. This now has an executed JVM assertion (see §4), not just inspection.
- `NotificationBridgeConfig.sanitizeDiagnostic` redacts `Bearer …`, `apiKey=`, `access_token=`, `token:`, `secret=`, `password=`, and `x-brainia-api-key/client-id` shapes and caps output at 500 characters. It is applied to the `lastError` and `diagnosticsLastUploadError` values exposed by `getNotificationListenerStatus`.
- `NotificationBridgeDiagnostics.kt` was **not edited** (outside this revision's write reservation). It was audited read-only: it persists caller-supplied fixed messages plus package names/status codes, never request headers, request bodies, tokens, or exception messages. Native capture persists no credential copy.

### 1.4 Safe migration

- The existing `apiKey`/`clientId` migration is unchanged: encrypted JS value wins, native-only legacy value is imported and rewritten through SecureStore, verified by the native reader, then removed. A failed read shows the visible “Vuelve a iniciar sesión” alert and blocks automatic overwrite until an intentional edit.
- A pre-M02 v2 token (token present, metadata absent) is **adopted** with neutral metadata (`generation: 1`, no expiry) instead of signing the user out. This preserves an existing session without downgrading.
- A revoked marker always wins over a leftover token, so a partially failed revoke cannot resurrect a session.
- Malformed or unsupported metadata makes reads return `null` **and** raises the visible reauthentication prompt; the app never falls back to a legacy plaintext copy or sends unauthenticated traffic.
- Enrollment/rotation write the token before metadata; the only crash window leaves a newer token with older (failing) metadata, which fails closed to re-authentication rather than authorizing stale metadata.

### 1.6 M01 condition C1 — offline at `GET /capabilities`

`contracts/**` is outside this revision's write reservation, so the sealed transport was not modified and `contracts:verify` still exercises its original `HELD` behavior. The application-level classification was fixed in `lib/api.ts`:

- The transport is created with a fetcher that marks network failures (`network_offline`).
- The wrapper observes failures during the awaited `deliverRevision` and maps `HELD / unsupported_or_unavailable_capabilities` → `PENDING / offline_capabilities`, and `PENDING / network_offline|invalid_or_missing_acknowledgement` → `PENDING / offline`.
- Server-originated holds (403, malformed/unsupported capabilities, 503) are **not** reclassified.
- No observation is attempted while offline; the exact envelope bytes are preserved, so fail-closed behavior is unchanged.

A probe against the real sealed transport and approved fixtures (temp scratch, no network) confirms: offline capabilities → 1 request (capabilities only), state `PENDING`, reason `offline_capabilities`, no observation POST; offline observations → `PENDING / offline`, not acknowledged; missing token → `BLOCKED_AUTH`, zero requests; 503 capabilities → not reclassified as offline.

## 8. Rollback and compatibility notes

- Token lifecycle is additive: removing the enrollment UI/reader leaves legacy v1 behavior intact, and v2 delivery falls back to `BLOCKED_AUTH` (never unauthenticated send).
- Metadata is versioned (`version: 2`); an unknown version fails closed to visible re-authentication instead of guessing.
- Revocation is monotonic: once revoked, a stale token is ignored until explicit re-enrollment.
- Consent migration is one-way and idempotent: a legacy set is rewritten once with version 2; an empty legacy set stays `empty` and is never reinterpreted as `unconfigured`.
- The `build.gradle` guard is configuration-time only and names keys, not values; removing the guard does not re-add any credential.
- On web, v2 credentials are intentionally not persisted; that is a usability trade-off, not a regression of a previously persisted web token (none existed).
