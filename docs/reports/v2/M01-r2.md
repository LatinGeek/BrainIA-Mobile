## 2. Blocked-operations guard (fail closed)

The sealed contract publishes strict schemas and fixtures for thirteen provisional operations, but every one is `implementationBlocked: true` in `open-items.json`. Before this follow-up, the generic `request()` resolved any operation present in `openapi.json`, so application code could call a review-blocked operation without passing any approval gate.

`contracts/brain-ai/2.0.0/mobile/transport.cjs` now holds an explicit `PROVISIONAL_OPERATIONS` list matching `open-items.json` and refuses each one unless the caller passes a local allowlist:

```js
createV2Transport(baseUrl, token, fetcher, {
  enabledProvisionalOperations: ['GET /api/v2/export'],
});
```

Behavior:

| Case | Result |
| --- | --- |
| No options / empty gate | `implementation_blocked` thrown before query validation, auth, body validation or any `fetch` |
| Gate lists an operation | Only that exact `METHOD + path template` is allowed through |
| Gate lists an unknown/misspelled name | Ignored; nothing is enabled |
| Gate lists one operation and the caller invokes another | Still `implementation_blocked` |
| Server capabilities advertise features | Cannot enable a review-blocked operation; the gate is caller-side only |

The application (`lib/api.ts`) passes no gate, so the mobile runtime remains fail-closed. No UI or backend flag can turn these operations on; a future reservation must add both the allowlist and the product surface deliberately.

Conformance coverage in `mobile/verify.mjs` (17 new checks, 221 total):

- The local list equals the sorted `implementationBlocked` names from the sealed `open-items.json`.
- All 13 operations reject with code `implementation_blocked` and **zero** network calls, even with malformed bodies/queries.
- An unknown gate value enables nothing.
- `GET /api/v2/export` reaches the network only when explicitly gated, using the approved `export-response` fixture.
- The gate does not spill into `POST /api/v2/queries`.

## 4. Offline-capabilities classification (documentation correction)

The code was already correct; the reports were not. Two layers must be distinguished:

| Layer | Offline during `GET /api/v2/capabilities` | Notes |
| --- | --- | --- |
| Sealed transport `deliverRevision` | `HELD / unsupported_or_unavailable_capabilities` | Approved sealed behavior; unchanged |
| Application wrapper in `lib/api.ts` | `PENDING / offline_capabilities` | Queue persists the exact envelope and retries; no observation POST |

Corrections to earlier wording:

- `M01-r1.md:79` listed "unavailable" capabilities as `HELD` without distinguishing transport from application. The transport result is `HELD`; the runtime queue result is `PENDING` for network failures only.
- `M01-r1.md:82` listed "offline" under `PENDING` for both calls. That is correct for the application queue: offline capabilities → `PENDING / offline_capabilities`; offline observation POST → `PENDING / offline`.
- Server-originated holds (403, malformed/unsupported capabilities, 503) remain holds and are **not** reclassified as offline.
- Missing/expired/revoked credential remains `BLOCKED_AUTH` with no network request.
