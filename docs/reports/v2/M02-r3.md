## 2. Settings expiry input

`lib/storage.ts` now accepts epoch milliseconds **as a string** in addition to a number and ISO-8601 when parsing `expiresAt`:

| Input | Interpretation |
| --- | --- |
| `1767225600000` (string or number) | epoch milliseconds |
| `2027-01-31T00:00:00Z` | ISO-8601 via `Date.parse` |
| empty / omitted | no declared expiry |
| non-numeric, non-ISO string | `Invalid access token expiry` (fail closed) |
| value in the past | `The access token is already expired` (fail closed) |

`app/settings.tsx` now documents both formats in the sheet, uses the placeholder `2027-01-31T00:00:00Z o 1800000000000`, and reports an invalid/past expiry with a specific message. The token itself is still validated by `isValidV2AccessToken` before any write.

## 3. Rotation confirmation

Rotation previously wrote immediately from the sheet. It now uses the same confirmation pattern as revoke and logout:

- Dialog title: `Rotar credencial v2`.
- Cancel is the default.
- `Rotar` is destructive-styled and performs `rotateV2AccessToken`.
- Cancelling leaves the current credential, generation and queued envelopes untouched.
- Enrollment (first connection or recovery) still saves directly after the explicit sheet action.
- `credentialBusy` guards duplicate taps, and the save button stays disabled while empty or busy.

## 4. Correction — rotation crash wording in `M02-r2.md:59`

`M02-r2.md:59` said:

> Enrollment/rotation write the token before metadata; the only crash window leaves a newer token with older (failing) metadata, which fails closed to re-authentication rather than authorizing stale metadata.

That is **not accurate** and is corrected here. The actual behavior of `storeV2Credential` is token first, metadata second. A process crash between the two writes leaves the **new token paired with the previous metadata** (or, on a first enrollment with no metadata, the legacy adoption path in `ensureV2CredentialMeta()` records neutral metadata: generation 1, no expiry). Consequences:

- The stored token itself is the newly written one; no old secret is resurrected.
- The credential remains readable/active unless the previous metadata was already expired or revoked.
- The displayed/recorded `generation`, `expiresAt` and `rotatedAt` can be stale for that credential until the next explicit enrollment/rotation rewrites metadata.
- Generation monotonicity is therefore best-effort across that crash window, not a hard invariant.
- There is no silent confidentiality downgrade and no plaintext fallback; the failure is metadata staleness, not unsafe storage.

The token-first order is retained deliberately: the reverse order could leave the **old token** paired with a newer expiry/generation, which would be a worse authorization mismatch than stale metadata on the new token.

## 6. Offline-capabilities documentation alignment

The code was already `PENDING`; the earlier prose conflated layers. Corrected statement:

- Sealed transport: offline during `GET /api/v2/capabilities` → `HELD / unsupported_or_unavailable_capabilities`.
- Application wrapper (`lib/api.ts`): the same event → `PENDING / offline_capabilities`; offline observation POST → `PENDING / offline`; no observation is attempted while offline; the exact envelope bytes are preserved.
- Server holds (403, 503, malformed/unsupported capabilities) are not reclassified as offline.
- Missing/expired/revoked credential stays `BLOCKED_AUTH` with zero requests.

This supersedes the ambiguous `M01-r1.md:79` / `:82` wording and is consistent with `M02-r2.md` §1.6.
